# 학습 노트

## 문서 목적

이 문서는 DMIB를 진행하면서 백엔드 개발자가 함께 익히면 좋은 실무 개념과 학습 주제를 정리한다.

이 프로젝트의 목표는 단순히 봇을 하나 완성하는 것이 아니라, 아래 역량을 실제 코드와 운영 흐름 안에서 익히는 것이다.
- 서비스 기업 백엔드 개발 방식 이해
- 운영 환경에서 발생하는 이슈 대응 감각 습득
- Agent 기반 개발 방식 이해
- 테스트, 리뷰, 배포, 모니터링 습관 내재화

## 핵심 개념

### 1. Liveness와 Correctness는 다르다
- Liveness: 프로세스와 컨테이너가 살아 있는가
- Correctness: 오늘 해야 할 작업이 실제로 정상 완료됐는가

실무에서는 두 개를 반드시 분리해서 봐야 한다.
DMIB에서는 아래처럼 나뉜다.
- `/actuator/health`, Docker healthcheck = Liveness
- `job_run`, monitoring scheduler = Correctness

### 2. 체크 주기와 알림 주기는 분리해야 한다
- 상태 체크는 자주 해도 된다.
- Slack 알림은 필요한 시점에만 보내야 한다.
- 그렇지 않으면 alert fatigue가 생긴다.

DMIB의 현재 정책:
- 상태 체크는 10분마다
- 첫 실패는 즉시 알림
- 이후 미해결이면 정각 리마인드

### 3. 서버에서 빌드하는 배포는 시작점일 뿐이다
- 현재 구조는 학습용으로 충분히 좋다.
- 하지만 장기적으로는 CI가 artifact나 이미지를 만들어야 한다.
- 서버는 pull과 실행만 담당하는 편이 실무적으로 더 안정적이다.

### 4. 내부용 엔드포인트는 기본 비활성화가 안전하다
- 테스트 실행 API
- 수동 Slack 테스트 API
- 운영 점검용 내부 엔드포인트

이런 기능은 기본적으로 닫아 두고, 필요할 때만 명시적으로 열어야 한다.

### 5. 문서도 코드의 일부다
- README는 공개 문서의 입구다.
- RUNBOOK은 운영자의 행동 기준이다.
- DEPLOYMENT는 배포 전략의 기록이다.
- STUDY는 학습 축적이다.
- PLAN은 다음 단계 우선순위다.

## 이번 프로젝트로 익히는 실무 습관

- 기능 추가 전에 영향 범위를 먼저 확인한다.
- 작업 단위마다 feature 브랜치를 분리한다.
- 코드 수정 후 테스트나 검증을 바로 수행한다.
- diff를 보고 내가 바꾼 내용을 설명할 수 있어야 한다.
- 운영 영향이 있는 변경은 문서까지 같이 업데이트한다.
